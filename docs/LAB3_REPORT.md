# Лабораторная работа №3

## Автоматические проверки, миграции и резервное копирование

Этот документ связывает каждый пункт задания с реализацией и проверочной
командой. Подробная матрица требований и тестов находится в
[`TEST_STRATEGY.md`](../TEST_STRATEGY.md).

## Итоговый результат

Полный проверочный контур выполнен 15 октября 2026 года командой:

```bash
make verify DOCKER="sudo docker"
```

Фактический результат:

- 133 из 133 pytest-сценариев прошли;
- покрытие строк и ветвей — 68,86% при обязательном пороге 40%;
- Ruff, mypy и Bandit не обнаружили ошибок;
- четыре миграции применились последовательно;
- проверены чистая и заполненная БД и повторный `upgrade head`;
- recovery-check восстановил удалённую и изменённую записи;
- временные контейнер и сеть удалены;
- `make verify` завершился с кодом 0.

Два предупреждения относятся к сторонним библиотекам `starlette` и `passlib` и
не являются ошибками приложения или тестов.

## 1. Первоначальная настройка

Команда:

```bash
make setup
```

Она проверяет Python 3.12+, создаёт `.venv`, устанавливает зависимости и через
`scripts/bootstrap_env.py` создаёт локальный `.env`. Существующий `.env` не
перезаписывается, новый файл получает права `0600`, секреты генерируются локально.

## 2. Фиксация версий

Прямые runtime-зависимости зафиксированы оператором `==` в `requirements.txt`,
инструменты разработки — в `requirements-dev.txt`. Это делает установку
воспроизводимой и не позволяет новой несовместимой версии установиться случайно.

## 3. Единый командный интерфейс

`Makefile` предоставляет `setup`, `run`, `test`, `quality`, `migrate`, `backup`,
`restore`, `verify`, `up`, `down`, `container-check` и более узкие тестовые цели.

## 4. Unit- и интеграционные тесты

Тесты разделены маркерами `unit`, `api`, `integration`, `migration`.

- 115 быстрых unit-тестов;
- 7 HTTP API-тестов;
- 6 дополнительных integration-тестов PostgreSQL;
- 5 тестов Alembic;
- отдельный настоящий recovery-check.

Все 27 функциональных требований имеют связь хотя бы с одним автоматическим
тестом. Проверка `test_every_functional_requirement_has_an_automated_test`
предотвращает случайную потерю этой трассировки. Это соответствует 100%
трассировочному покрытию функций при требуемом минимуме 40%.

## 5. Ошибочные данные, границы и мутации

Проверяются отсутствующие поля, длина пароля, границы года издания, отрицательные
денежные значения, лимиты выдачи и продлений, чужая бронь, дубли, права ролей,
невалидный JWT и rollback.

Пример для защиты: в проверке лимита выдачи временно заменить условие
`active_loans >= max_books_per_user` на `active_loans > max_books_per_user`.
Тест `test_reader_at_active_loan_limit_cannot_borrow` обязан упасть, поскольку
проверяет точное граничное значение. Изменение после демонстрации отменяется.

## 6. Изоляция тестовых данных

`compose.test.yml` создаёт отдельную БД `lms_test` на `127.0.0.1:5433` во
временной файловой системе. `tests/conftest.py` запрещает БД без суффикса `_test`
и принудительно заменяет `DATABASE_URL` проверенным тестовым адресом. Между
integration-тестами таблицы очищаются.

## 7. Quality gate и отчёты

```bash
make quality
```

запускает Ruff format, Ruff lint, mypy, Bandit и проверку JavaScript.
`make test` формирует:

- `reports/junit.xml`;
- `reports/coverage.xml`;
- `reports/coverage-html/index.html`.

Порог line/branch coverage `40%` задан через `fail_under` в `pyproject.toml`.

## 8. Последовательные миграции

Alembic применяет цепочку:

```text
001 initial schema
  → 002 inventory, audit and queue
  → 003 security and edition fields
  → 004 favorite books
```

`make migrate` выполняет `scripts/migrate.py`. Для проверенной старой схемы без
Alembic скрипт безопасно ставит отметку `003`, сохраняет данные и применяет `004`.
Неизвестная или неполная схема автоматически не штампуется.

## 9. Чистая и заполненная БД

Тесты проверяют создание схемы с нуля, последовательный переход между каждой
ревизией, сохранение пользователя из `001` после обновления до `004` и
идемпотентный повторный `upgrade head`.

## 10. Новая функция

Миграция `004` добавляет таблицу `favorite_books`. Читатель может добавить,
получить и удалить избранную книгу через `/api/v1/favorites`. Уникальный ключ
запрещает дубли, внешние ключи поддерживают ссылочную целостность.

## 11–12. Backup и восстановление

`make backup` и `make restore` используют `pg_dump`/`pg_restore`. Пароль передаётся
через `PGPASSWORD`, а не через аргументы процесса. Restore требует существующий
файл и `CONFIRM_RESTORE=yes`.

`make test-recovery` создаёт две записи, снимает dump, удаляет одну, изменяет
другую, восстанавливает dump и сравнивает оба исходных значения. Сценарий
работает только с временной `lms_test`.

## 13. Полная команда проверки

```bash
make verify DOCKER="sudo docker"
```

Порядок:

1. форматирование;
2. линтер;
3. проверка типов;
4. SAST;
5. синтаксис JavaScript;
6. pytest и отчёты;
7. порог покрытия;
8. recovery-check;
9. удаление тестового контейнера и данных.

Любая ошибка останавливает команду с ненулевым кодом.

## 14. Запрет обхода проверок

В `TEST_STRATEGY.md` зафиксирован запрет необоснованного `skip`/`xfail`, снижения
порога покрытия и исключений Ruff, mypy или Bandit. Точечное подавление SAST
допустимо только рядом со строкой и с объяснением безопасности.

## 15. Функциональное изменение через verify

Новая функция «Избранные книги» включена в unit-, API-, integration- и
миграционные тесты. Итоговым доказательством служит успешный запуск:

```bash
make verify DOCKER="sudo docker"
```

постороннего узла; это относится к ЛР2.
