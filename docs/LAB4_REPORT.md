# Лабораторная работа №4. Контейнеризация приложения

## Реализованный контур

Приложение и PostgreSQL описаны в `docker-compose.yml`. Образ приложения
собирается из `Dockerfile`; `.dockerignore` исключает секреты, Git-метаданные,
виртуальное окружение, отчёты, дампы и локальные данные.

Основные гарантии:

- базовые образы имеют конкретные версии и не используют `latest`;
- версии Python-зависимостей зафиксированы через `==`;
- приложение запускается с UID/GID `10001`, а не от `root`;
- настройки передаются во время запуска через переменные окружения;
- `exec uvicorn` и `STOPSIGNAL SIGTERM` обеспечивают доставку сигнала Uvicorn;
- PostgreSQL доступна только во внутренней сети Compose, порт `5432` не публикуется;
- данные PostgreSQL находятся в именованном volume;
- запуск приложения ожидает успешный healthcheck PostgreSQL;
- для приложения включены read-only root filesystem, `no-new-privileges` и
  удалены Linux capabilities;
- журналы ротируются и не растут без ограничения.

## Ограничения ресурсов

| Сервис | CPU | RAM | PIDs | Обоснование |
|---|---:|---:|---:|---|
| `library-lms` | 0,50 | 256 MiB | 100 | Один учебный Uvicorn-процесс; лимит оставляет запас для миграций и запросов |
| `postgres` | 1,00 | 512 MiB | 200 | БД требует больше памяти для shared buffers, соединений и backup/restore |

Лимиты защищают Linux-машину от бесконтрольного потребления ресурсов, но не
настолько малы, чтобы мешать учебной нагрузке. При нагрузочном тестировании их
следует пересмотреть на основании метрик CPU, памяти и задержек.

## Автоматическая проверка

```bash
make container-check
```

Если Docker требует `sudo`:

```bash
make container-check DOCKER="sudo docker"
```

Проверка использует отдельный Compose project `library-lms-container-check`,
отдельный volume и порт `18000`, поэтому не изменяет основную БД. Она проверяет:

1. валидность Compose;
2. сборку и healthcheck;
3. запуск приложения не от root;
4. фактические лимиты и read-only root filesystem;
5. отсутствие опубликованного порта PostgreSQL;
6. сохранность маркерной записи после пересоздания контейнера PostgreSQL;
7. сохранность данных после сборки и пересоздания контейнера приложения;
8. завершение по SIGTERM без SIGKILL и OOM (`0` либо стандартный сигнальный код `143`);
9. создание backup, удаление старого volume и восстановление в новый volume;
10. запуск приложения на восстановленной БД.

Временное окружение и backup удаляются обработчиком `trap` даже при ошибке.

## Обязательные запреты

Запрещено без отдельного обоснования в Pull Request:

- использовать тег `latest` или непредсказуемо плавающий образ;
- запускать процесс приложения от `root`;
- копировать `.env`, пароли, токены, ключи и backup в образ;
- удалять healthcheck приложения или PostgreSQL;
- публиковать порт PostgreSQL либо другие лишние порты;
- отключать resource limits, `no-new-privileges` или read-only root filesystem;
- принимать изменение контейнерного окружения без успешного `make container-check`.
