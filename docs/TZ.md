# Техническое задание

## 1. Общие сведения

Полное наименование: «Информационная система управления библиотекой» (Library Management System, LMS). Работа выполняется как сквозной учебный проект. Основанием для разработки является задание лабораторной работы №1.

## 2. Назначение и цели создания

Система предназначена для ведения каталога библиотеки, учёта физических экземпляров, читателей, выдач, возвратов, бронирований, штрафов и уведомлений.

Цели:

- предоставить читателю единый веб-интерфейс работы с библиотекой;
- сократить ручные операции библиотекаря;
- обеспечить однозначное состояние каждого экземпляра;
- сохранять историю выдач и начислений;
- разграничить доступ по ролям.

## 3. Характеристика объекта автоматизации

Объект автоматизации — библиотека с несколькими филиалами. Одно библиографическое издание может иметь несколько физических экземпляров. Экземпляр находится в одном филиале и в каждый момент имеет определённое состояние. Выдачи оформляются сотрудником библиотеки зарегистрированным и верифицированным читателям.

## 4. Требования к системе

### 4.1 Категории пользователей

| Роль | Возможности |
|---|---|
| Гость | просмотр каталога, регистрация, вход |
| Студент/сотрудник | профиль, бронирование, свои выдачи, продление, штрафы, уведомления |
| Библиотекарь | пользователи, каталог, экземпляры, выдача, возврат, отчёты |
| Администратор | функции библиотекаря, управление сотрудниками и правилами выдачи |

### 4.2 Функциональные требования

Система должна обеспечивать:

1. регистрацию читателя и вход по логину и паролю;
2. хранение паролей в виде bcrypt-хэша;
3. выдачу JWT и проверку роли на защищённых операциях;
4. просмотр, поиск и фильтрацию каталога;
5. создание и изменение изданий и экземпляров сотрудниками;
6. верификацию и деактивацию пользователей;
7. оформление выдачи, возврата и продления;
8. бронирование доступного экземпляра или постановку в очередь;
9. расчёт штрафа за просрочку, утрату или повреждение;
10. уведомления о событиях;
11. инвентарные и статистические отчёты;
12. изменение администратором правил выдачи.

### 4.3 Обязательные правила предметной области

- Саморегистрация разрешена только для ролей `STUDENT` и `EMPLOYEE`.
- Выдача разрешена только активному верифицированному читателю.
- Без предварительной брони выдать можно только экземпляр в состоянии `AVAILABLE`.
- Экземпляр в состоянии `RESERVED` можно выдать только забронировавшему его
  читателю; выдача одновременно переводит бронь в состояние `FULFILLED`.
- Число активных выдач не должно превышать установленный лимит.
- Число продлений не должно превышать установленный лимит.
- После выдачи экземпляр получает состояние `ISSUED`, после обычного возврата — `AVAILABLE`.
- Активные брони и очередь читателей отображаются библиотекарю в разделе
  книговыдачи; новая заявка также создаёт служебное уведомление.
- Утерянный или повреждённый экземпляр получает соответствующее состояние.
- При просрочке, утрате или повреждении может быть создан штраф.
- Повторная активная бронь одного издания тем же читателем запрещена.
- При отсутствии доступного экземпляра читатель добавляется в очередь.

### 4.4 Требования к входным данным и ошибкам

Обязательные поля и форматы HTTP-запросов проверяются Pydantic. Система должна возвращать корректные HTTP-коды для неверных данных, отсутствующей аутентификации, недостаточных прав и отсутствующих сущностей. Ошибка одной операции записи не должна оставлять частично изменённые данные.

### 4.5 Требования к интерфейсу

Система должна иметь адаптированный для браузера веб-интерфейс на русском языке. Обязательные страницы: главная, регистрация, вход, каталог, карточка издания, кабинет читателя и раздел управления сотрудника.

### 4.6 Требования к данным

Данные должны храниться в реляционной БД с внешними ключами. Основные сущности: пользователь, издание, экземпляр, выдача, бронь, штраф и уведомление. Состав таблиц и связи описаны в `docs/ER.md`.

### 4.7 Конфигурация и безопасность

- секреты и параметры окружения передаются переменными окружения;
- `.env`, локальная БД и ключи не включаются в Git;
- секрет JWT не должен иметь производственного значения по умолчанию;
- первый администратор создаётся интерактивной bootstrap-командой без хранения его пароля в конфигурации;
- пароль должен содержать не менее 12 символов и не более 72 байт в UTF-8;
- смена пароля и выход должны отзывать ранее выданные JWT;
- защищённые операции должны проверять JWT и роль;
- пароли не выводятся в ответах и журналах.

### 4.8 Надёжность и контроль состояния

Запись нескольких взаимосвязанных изменений должна выполняться транзакционно. Приложение должно предоставлять `GET /health` для проверки работоспособности.

## 5. Состав программных средств

Текущая версия использует Python 3.12, FastAPI, Uvicorn, Jinja2, JavaScript, PostgreSQL 17, psycopg 3, PyJWT и bcrypt. Клиент взаимодействует с REST API по HTTP/JSON. Документация API формируется в OpenAPI.

## 6. Стадии разработки

1. ЛР1: работоспособное приложение, PostgreSQL и Git-процесс.
2. ЛР2: раздельные Linux-серверы приложения и базы данных.
3. ЛР3: тесты, миграции, резервное копирование и единая проверка.
4. ЛР4–ЛР8: контейнеризация, CI/CD, инфраструктура и наблюдаемость.

## 7. Порядок контроля и приёмки ЛР1

Приёмка включает:

- запуск приложения по README;
- успешный ответ `/health`;
- регистрацию, вход и защищённый запрос;
- демонстрацию связанного сценария «верификация — выдача — возврат»;
- демонстрацию схемы и документации API;
- подтверждение отсутствия секретов и локальной БД в Git;
- показ задачи, ветки, коммитов, PR/MR, разрешённого конфликта и тега `v0.1.0`.

## 8. Требования к документации

В составе проекта должны находиться README с запуском и правилами изменений, техническое задание, описание API, схема данных, `.env.example` и история Git-процесса в удалённом репозитории.
