# Library Management System

Учебная информационная система библиотеки: каталог изданий и физических экземпляров, регистрация читателей, выдача, возврат, продление, бронирование, штрафы, уведомления и отчёты.

Проект создан как сквозная работа для последовательного освоения Git-процесса, развёртывания, тестирования, миграций, контейнеризации, CI/CD, инфраструктурной автоматизации и наблюдаемости.

## Пользователи и основные сценарии

- `STUDENT` и `EMPLOYEE`: регистрация, каталог, бронирование, просмотр и продление своих выдач, штрафы и уведомления.
- `LIBRARIAN`: верификация читателей, каталог и экземпляры, выдача и возврат книг, отчёты.
- `ADMIN`: все возможности библиотекаря, создание библиотекарей, деактивация пользователей и изменение правил выдачи.

Подробные требования находятся в [техническом задании](docs/TZ.md), маршруты — в [описании API](docs/API.md), таблицы и связи — в [схеме данных](docs/ER.md).
Текущее соответствие требованиям ЛР1 собрано в [контрольном листе](docs/LAB1_CHECKLIST.md).

## Технологии

- Python 3.12, FastAPI, Uvicorn;
- Jinja2 и vanilla JavaScript;
- PostgreSQL 17 и psycopg 3;
- JWT и bcrypt.

Версия `v0.1.1` использует PostgreSQL без изменения публичного HTTP API.

## Локальный запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Задайте в `.env` собственные пароли PostgreSQL и случайный `SECRET_KEY` длиной не менее 32 символов. Для локального запуска без контейнера предварительно создайте БД PostgreSQL, указанную в `DATABASE_URL`, затем экспортируйте настройки и запустите приложение:

```bash
set -a
source .env
set +a
uvicorn app.main:app --reload
```

После запуска доступны:

- веб-интерфейс: <http://127.0.0.1:8000/>;
- OpenAPI UI: <http://127.0.0.1:8000/docs>;
- healthcheck: <http://127.0.0.1:8000/health>.

При первом запуске создаются таблицы PostgreSQL и демонстрационный каталог (если `SEED_DEMO_DATA=true`). Администратор автоматически не создаётся: пароль не должен постоянно храниться в `.env`.

Создайте первого администратора интерактивно:

```bash
python -m app.cli.create_admin
```

Пароль вводится скрыто, сразу преобразуется в bcrypt-хэш и не попадает в аргументы процесса, shell history или конфигурацию.

## Единый командный интерфейс

Основные действия выполняются через `make`:

```bash
make setup             # создать .venv, установить зависимости и подготовить .env
make run               # локально запустить приложение
make quality           # проверить синтаксис Python и JavaScript
make migrate           # применить текущую схему PostgreSQL
make backup            # сохранить БД в backups/
make up                # запустить Docker Compose
make down              # остановить Docker Compose, сохранив данные БД
make container-check   # собрать, запустить и проверить контейнеры
```

Интерфейс также содержит будущие команды `make test`, `make verify` и
`make restore`. В ЛР1 `make test` и, следовательно, `make verify` намеренно
завершаются ошибкой: тестовый набор появится в ЛР3, и команда не должна создавать
ложное ощущение успешной проверки. Восстановление уже доступно, но требует
явного подтверждения:

```bash
make restore BACKUP_FILE=backups/lms_20260920_120000.dump CONFIRM_RESTORE=yes
```

До появления Alembic команда `make migrate` вызывает существующую идемпотентную
инициализацию схемы. В ЛР3 за тем же интерфейсом будет стоять инструмент миграций.

## Docker Compose

После создания `.env`:

```bash
docker compose up --build
docker compose ps
curl --fail http://127.0.0.1:8000/health
docker compose exec library-lms python -m app.cli.create_admin
```

Compose запускает приложение и PostgreSQL во внутренней сети. Порт БД наружу не публикуется. Полная контейнерная проверка и ограничения контейнеров будут оформляться в ЛР4.

## Проверка перед коммитом

Для ЛР1 обязательны:

```bash
python -m compileall -q app
SECRET_KEY=local-check-secret-with-32-characters DATABASE_URL=postgresql://lms:password@127.0.0.1:5432/lms SEED_DEMO_DATA=false uvicorn app.main:app --host 127.0.0.1 --port 8000
curl --fail http://127.0.0.1:8000/health
```

Нужно также вручную проверить изменённый пользовательский сценарий. `make verify`, тесты, линтеры и покрытие являются результатом ЛР3 и не подменяются фиктивными командами в ЛР1.

## Правила внесения изменений

### Ветки

- `main` — стабильная версия;
- `feature/<name>` — новая функция;
- `fix/<name>` — исправление;
- `docs/<name>` — документация;
- `chore/<name>` — инфраструктурные изменения.

Изменения напрямую в `main` не вносятся. Одна задача выполняется в отдельной ветке и принимается через Pull Request или Merge Request.

### Коммиты

Формат: `type: краткое описание`. Примеры: `feat: add book reservation`, `fix: prevent duplicate active loan`, `docs: describe API endpoints`, `refactor: extract database settings`, `chore: update dependencies`.

Коммиты должны быть небольшими, осмысленными и сохранять работоспособность проекта. Не следует смешивать функциональность, рефакторинг и форматирование без необходимости.

### Приёмка изменения

1. Создать задачу с критериями готовности.
2. Создать ветку от актуальной `main`.
3. Внести изменение несколькими осмысленными коммитами.
4. Выполнить проверки и проверить `git diff`.
5. Отправить ветку и создать PR/MR со ссылкой на задачу.
6. Получить проверку другого участника или преподавателя.
7. Исправить замечания, дождаться успешных проверок и выполнить слияние.
8. Удалить рабочую ветку. Релизную точку отметить тегом.

### Запрещено

- добавлять `.env`, пароли, токены, приватные ключи и локальные БД;
- коммитить `.venv`, `__pycache__`, IDE- и временные файлы;
- отключать проверки или удалять тесты ради успешной приёмки;
- переписывать опубликованную историю общей ветки;
- выполнять прямой push в `main`;
- принимать собственный PR без проверки, если доступен проверяющий.

## Демонстрация Git-процесса для ЛР1

В удалённом репозитории необходимо сохранить доказательства, которые нельзя создать одним изменением файлов:

1. задача на одну законченную функцию;
2. отдельная ветка и несколько коммитов;
3. принятый PR/MR;
4. намеренный конфликт и коммит его разрешения;
5. аннотированный тег `v0.1.0` на принятом состоянии `main`.

Тег создаётся после приёмки:

```bash
git switch main
git pull --ff-only
git tag -a v0.1.0 -m "Лабораторная работа №1"
git push origin v0.1.0
```

Переход на PostgreSQL выпускается отдельным patch-релизом после PR/MR:

```bash
git switch main
git pull --ff-only
git tag -a v0.1.1 -m "ЛР1: переход на PostgreSQL без изменения публичного API"
git push origin v0.1.1
```
