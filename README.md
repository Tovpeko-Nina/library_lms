# Library Management System

Учебная информационная система библиотеки: каталог изданий и физических экземпляров, регистрация читателей, выдача, возврат, продление, бронирование, штрафы, уведомления и отчёты.

Проект создан как сквозная работа для последовательного освоения Git-процесса, развёртывания, тестирования, миграций, контейнеризации, CI/CD, инфраструктурной автоматизации и наблюдаемости.

## Пользователи и основные сценарии

- `STUDENT` и `EMPLOYEE`: регистрация, каталог, бронирование, просмотр и продление своих выдач, штрафы и уведомления.
- `LIBRARIAN`: верификация читателей, каталог и экземпляры, выдача и возврат книг, отчёты.
- `ADMIN`: все возможности библиотекаря, создание библиотекарей, деактивация пользователей и изменение правил выдачи.

Подробные требования находятся в [техническом задании](docs/TZ.md), маршруты — в [описании API](docs/API.md), таблицы и связи — в [схеме данных](docs/ER.md).
Текущее соответствие требованиям ЛР1 собрано в [контрольном листе](docs/LAB1_CHECKLIST.md).
Реализация и команды защиты ЛР3 описаны в [отчёте ЛР3](docs/LAB3_REPORT.md).

## Технологии

- Python 3.12, FastAPI, Uvicorn;
- Jinja2 и vanilla JavaScript;
- PostgreSQL 17 и psycopg 3;
- JWT и bcrypt.

Версия `v0.1.1` использует PostgreSQL без изменения публичного HTTP API.

## Локальный запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Задайте в `.env` собственные пароли PostgreSQL и случайный `SECRET_KEY` длиной не менее 32 символов. Для локального запуска без контейнера предварительно создайте БД PostgreSQL, указанную в `DATABASE_URL`, затем экспортируйте настройки и запустите приложение:

```bash
set -a
source .env
set +a
uvicorn app.main:app --reload
```

После запуска доступны:

- веб-интерфейс: <http://127.0.0.1:8000/>;
- OpenAPI UI: <http://127.0.0.1:8000/docs>;
- healthcheck: <http://127.0.0.1:8000/health>.

Перед первым локальным запуском таблицы создаются командой `make migrate`.
После этого приложение добавляет демонстрационный каталог, если
`SEED_DEMO_DATA=true`. Администратор автоматически не создаётся: пароль не должен
постоянно храниться в `.env`.

Создайте первого администратора интерактивно:

```bash
python -m app.cli.create_admin
```

Пароль вводится скрыто, сразу преобразуется в bcrypt-хэш и не попадает в аргументы процесса, shell history или конфигурацию.

## Единый командный интерфейс

Основные действия выполняются через `make`:

```bash
make setup             # создать .venv, установить зависимости и подготовить .env
make run               # локально запустить приложение
make test              # запустить тесты и сформировать отчёты покрытия
make test-unit         # запустить быстрые тесты без PostgreSQL
make test-api          # проверить HTTP API с временной PostgreSQL
make test-integration  # integration-тесты с временной PostgreSQL
make test-migration    # проверить цепочку миграций Alembic
make test-recovery     # проверить backup, порчу и восстановление тестовой БД
make test-db-up        # запустить только тестовую PostgreSQL
make test-db-down      # удалить тестовую PostgreSQL и её данные
make quality           # Ruff, mypy, Bandit и проверка JavaScript
make format            # автоматически отформатировать Python-код
make migrate           # применить текущую схему PostgreSQL
make backup            # сохранить БД в backups/
make restore BACKUP_FILE=... CONFIRM_RESTORE=yes
make verify            # запустить quality и test
make up                # запустить Docker Compose
make down              # остановить Docker Compose, сохранив данные БД
make container-check   # собрать, запустить и проверить контейнеры
```

Если Docker доступен только через `sudo`, полный итоговый прогон выполняется так:

```bash
make verify DOCKER="sudo docker"
```

`make setup` устанавливает как зависимости приложения из `requirements.txt`,
так и инструменты разработки из `requirements-dev.txt`. Все версии зафиксированы,
чтобы на разных машинах использовался одинаковый проверочный контур. Команда
требует Python 3.12 или новее, создаёт `.venv` и формирует локальный `.env` из
шаблона. `SECRET_KEY` и пароль PostgreSQL генерируются случайно непосредственно
в `.env`, не выводятся в терминал и не сохраняются в Git. Новый `.env` получает
права `0600`; существующий файл команда никогда не перезаписывает.

После первоначальной настройки проверьте адрес PostgreSQL в `.env`, подготовьте
указанную базу и примените схему:

```bash
make setup
make migrate
make verify
```

`make test` создаёт JUnit-отчёт, XML-отчёт покрытия и читаемый HTML-отчёт в
каталоге `reports/`. Набор содержит 115 unit-тестов, 7 API-тестов,
6 дополнительных интеграционных случаев и 5 тестов миграций. Обязательный порог
покрытия установлен на уровне 40%: если покрытие
станет ниже, `make test` и `make verify` завершатся с ошибкой.

Полный `make test` самостоятельно поднимает PostgreSQL из `compose.test.yml` на
`127.0.0.1:5433`, запускает все тесты и удаляет тестовое окружение вместе с
данными. Если Docker доступен только через `sudo`, используйте:

```bash
make test DOCKER="sudo docker"
```

Для отдельного запуска integration-тестов:

```bash
make test-integration DOCKER="sudo docker"
```

Тесты принимают только `TEST_DATABASE_URL`, имя базы в котором оканчивается на
`_test`. Во время pytest проверенный тестовый адрес принудительно подставляется
вместо `DATABASE_URL`, поэтому экспортированный в терминале адрес рабочей базы
не используется.

После pytest полный `make test` выполняет recovery-check в той же временной БД:
создаёт контрольные записи, снимает dump, удаляет одну запись и изменяет другую,
восстанавливает dump и сравнивает оба исходных значения. Для отдельного запуска:

```bash
make test-recovery DOCKER="sudo docker"
```

Восстановление БД требует явного подтверждения:

```bash
make restore BACKUP_FILE=backups/lms_20260920_120000.dump CONFIRM_RESTORE=yes
```

`make migrate` применяет последовательные миграции Alembic. Для старой БД,
которая была создана прежней функцией `init_db`, команда сначала проверяет наличие
всех ожидаемых таблиц и столбцов, затем ставит безопасную отметку ревизии `003`
без удаления данных. Неполная или неизвестная схема автоматически не помечается.

История миграций:

1. `001_initial_schema` — базовые сущности библиотеки;
2. `002_add_inventory_and_queue` — аудит, история инвентаризации и очередь;
3. `003_add_security_and_edition_fields` — версия токена, год и номер издания;
4. `004_add_favorite_books` — новая функция «Избранные книги».

## Docker Compose

После создания `.env`:

```bash
docker compose up --build
docker compose ps
curl --fail http://127.0.0.1:8000/health
docker compose exec library-lms python -m app.cli.create_admin
```

Compose запускает PostgreSQL, дожидается её готовности, применяет Alembic-миграции
и только затем запускает приложение. Порт БД наружу не публикуется. Полная
контейнерная проверка и ограничения контейнеров будут оформляться в ЛР4.

## Проверка перед коммитом

Для локальной проверки изменений используются:

```bash
make quality
make test-unit
make test
```

`make quality` проверяет форматирование Ruff, правила линтера, типы через mypy,
безопасность Python-кода через Bandit и синтаксис JavaScript при наличии Node.js.
`make verify` объединяет `quality`, unit-, API-, integration- и миграционные
тесты, порог покрытия 40% и настоящий сценарий резервного восстановления.

## Правила внесения изменений

### Ветки

- `main` — стабильная версия;
- `feature/<name>` — новая функция;
- `fix/<name>` — исправление;
- `docs/<name>` — документация;
- `chore/<name>` — инфраструктурные изменения.

Изменения напрямую в `main` не вносятся. Одна задача выполняется в отдельной ветке и принимается через Pull Request или Merge Request.

### Коммиты

Формат: `type: краткое описание`. Примеры: `feat: add book reservation`, `fix: prevent duplicate active loan`, `docs: describe API endpoints`, `refactor: extract database settings`, `chore: update dependencies`.

Коммиты должны быть небольшими, осмысленными и сохранять работоспособность проекта. Не следует смешивать функциональность, рефакторинг и форматирование без необходимости.

### Приёмка изменения

1. Создать задачу с критериями готовности.
2. Создать ветку от актуальной `main`.
3. Внести изменение несколькими осмысленными коммитами.
4. Выполнить проверки и проверить `git diff`.
5. Отправить ветку и создать PR/MR со ссылкой на задачу.
6. Получить проверку другого участника или преподавателя.
7. Исправить замечания, дождаться успешных проверок и выполнить слияние.
8. Удалить рабочую ветку. Релизную точку отметить тегом.

### Запрещено

- добавлять `.env`, пароли, токены, приватные ключи и локальные БД;
- коммитить `.venv`, `__pycache__`, IDE- и временные файлы;
- отключать проверки или удалять тесты ради успешной приёмки;
- переписывать опубликованную историю общей ветки;
- выполнять прямой push в `main`;
- принимать собственный PR без проверки, если доступен проверяющий.

## Демонстрация Git-процесса для ЛР1

В удалённом репозитории необходимо сохранить доказательства, которые нельзя создать одним изменением файлов:

1. задача на одну законченную функцию;
2. отдельная ветка и несколько коммитов;
3. принятый PR/MR;
4. намеренный конфликт и коммит его разрешения;
5. аннотированный тег `v0.1.0` на принятом состоянии `main`.

Тег создаётся после приёмки:

```bash
git switch main
git pull --ff-only
git tag -a v0.1.0 -m "Лабораторная работа №1"
git push origin v0.1.0
```

Переход на PostgreSQL выпускается отдельным patch-релизом после PR/MR:

```bash
git switch main
git pull --ff-only
git tag -a v0.1.1 -m "ЛР1: переход на PostgreSQL без изменения публичного API"
git push origin v0.1.1
```
